# Stateless native-control peer for canonical Core ownership

Bounded synthetic component, not a production cutover or native fencing receipt.
`browser_runtime.control_peer.ControlPeer` adds no database, journal, operation
map, profile storage, daemon, transport launcher or credential issuer. It reuses
legacy `Transfer`, `Recovery`, `Guard`, `Backend` and `Inspector` types without
instantiating `LeaseStore`; all existing legacy files and data remain untouched.

## Mapping to Core

Core PR59's `browser_control` stores typed transitions and a head pointer in the
existing Core BrowserRegistry file. Its canonical owner must reserve and dedupe
before invoking this peer. The existing `runspindle.browser-effect.v1` request
carries target and payload commitment; control bytes use the closed
`runspindle.browser-control.v1` structure with action, source/destination holders
and predecessor operation/digest/generation. The intent is `browser-control:`
plus SHA256 of Core's sorted, UTF-8 unescaped canonical JSON scope; revision equals control epoch. Legacy Python lease serialization remains unchanged (including its ASCII escape form). `tests/fixtures/core_control_scope.json` contains exact ASCII and Unicode vectors generated by the compiled Core PR59 library, not this Python helper.
Ordinary page-effect epochs are not interpreted as control transitions.

The composition root supplies the exact retained Core payload separately to
`exchange`, including on reconcile (whose wire payload is null). This parameter
is trusted application context, not a new message-granted capability. The peer
matches its digest, exact target and holders to an independently authenticated
opaque native `Transfer` or `Recovery` ticket. Actual predecessor history is only
validated by Core; Browser must not create a second chain store.

Dispatch acquires the native guard, checks explicit current initialization proof
or source release on handback, exact physical scope, freshness and deadline,
then invokes `Backend.fence`. Even a positive fence receipt returns **unknown**;
only a distinct authorized reconciliation with fresh exact closure observation
returns confirmed. Recovery never invokes fencing. Exceptions and cancellation
are redacted, including context managers suppressing the original exception.

The peer captures the validated transfer and recovery bindings at admission.
Guard callbacks must preserve those fields before a native fence or confirmation.
Readback captures a typed closure observation before rechecking current authority.
Only the same exact observation, with closure already true and a timestamp fresh
at that final check, can confirm. A foreign equality object or a closure flag
changed by a later callback cannot supply release evidence. These checks add no
Browser-owned state and do not replace the backend's obligation to enforce the
physical input fence.

## Mandatory application/native integration gates

- Core is the sole reservation authority. This peer deliberately repeats a fence
  if handed two separately admitted dispatch calls; it cannot dedupe locally.
- A trusted backend must actually stop and drain every prior input path, including
  human viewer input on handback. A SQLite transaction or bool callback is not a
  native fence. Guard callbacks are pure observations inside that real fence.
- Current initialization proof is a distinct protocol method and fails closed
  when absent; absence of a database row is never native ownership proof.
- An authenticated application must compose the retained Core bytes, opaque ticket,
  peer lifetime and total deadline. Existing anonymous-pipe framing can transport
  the wire, but this slice does not install that application or issuer.
- Operational legacy inventory, preservation of IDs/epochs, explicit quiescence
  and one-way owner retirement remain separate. No legacy data copy, deletion,
  backup, automatic migration or dual-authority fallback occurs here.

Tests use synthetic authority/fence/inspection only. No real Rust-to-native control
handoff, Chromium drain behavior, Host profile relocation, operational migration
or Actions CI execution is claimed. The prior account E2E receipt is not inherited
by this new control component.


## Initial peer evidence

- 13 focused tests pass normal and optimized; independent reviewer repeated both.
- 56 control/recovery/wire tests pass normal and optimized.
- Full unittest discovery: 610 run, 10 explicit integration skips, no failures.
  Existing legacy SQLite ResourceWarnings remain; this new peer opens no database.
- New runtime/tests pass strict mypy with both actual imported protocols and the
  repository skip-imports mode; ruff and scaffold checks pass.
- This is local component evidence only, not an Actions run or qualified fleet.

## Admission and closure regression evidence

The source and test changes were checked against Browser main at
`fe5647c18e1b48962a51e0e993f61e37d4dbfae2`. All 17 peer tests passed on macOS
arm64 with CPython 3.13.18 in normal and optimized modes. Strict mypy, Ruff,
and the scaffold check passed.

Three regression tests reproduced the behavior on the earlier peer revision
`d2309a367df30d0bde2171b0eae5dabeee7d19c0`. The mutation test removes the
final admitted-grant comparison and observes an unexpected call to the
synthetic native fence. Actual Chromium drain and the authenticated Core
composition still require separate integration evidence.
